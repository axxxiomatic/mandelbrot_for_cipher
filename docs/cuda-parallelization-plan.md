## 1. Что осталось сделать

Разбито по приоритету. **P0** — без этого параллелизация не даёт корректного результата
(и опасна: ошибка не проявляется как исключение). **P1** — без этого она не работает
устойчиво. **P2** — без этого она не даёт выигрыша в реальном сценарии.

### P0. Корректность (блокеры)

| # | Задача | Суть | Критерий готовности |
|---|---|---|---|
| 1 | **Единая палитра** | CPU считает `iter` вниз (`MAX_ITER→0`), GPU — вверх (`0→MAX_ITER`); `smooth` и `hue` зеркальны. Привести к одной формуле: `n` — число шагов, `smooth = n + 1 − log(log\|z\|)/log 2`, `hue = 0.95 + 2·smooth/maxIter`, `hue −= floor(hue)` | `FractalPaletteParityTest` зелёный: `diff = 0 px` на 4 наборах параметров, `sha256` совпадает |
| 2 | **Точность арифметики** | `smooth`/`hue` считать в `double`, в `float` переходить только на входе HSB (иначе 246 из 4 млн пикселей расходятся — измерено численно) | тот же тест: `0` расхождений, а не «допустимая погрешность» |
| 3 | **Клэмп бина** | `(int)(hue*36)` при `hue == 1.0` даёт `bin == 36` → запись за границу массива в ядре | `FractalMetrics` и ядро дают одинаковые `occupiedBins`/`maxBinRatio` на синтетических изображениях |
| 4 | **Типы растра** | `isFractalValid` кастует к `DataBufferInt`, GPU отдаёт `TYPE_3BYTE_BGR` → `ClassCastException`; `GPUXOROperation` кастует к `DataBufferByte`, а `bytesToImage` отдаёт `TYPE_INT_RGB` | прогон `findValidFractalParallel` и полного encrypt→decrypt на GPU завершается без исключений |
| 5 | **Контекст CUDA по потокам** | `cuCtxCreate` в потоке Spring-бина не даёт контекста в потоках пула (`CUDA_ERROR_INVALID_CONTEXT`) | вызов `generate()` из 4 разных потоков подряд проходит; в логе нет `INVALID_CONTEXT` |
| 6 | **Fallback на любой сбой GPU** | исключение в static-инициализаторе роняет приложение в обход `isCudaAvailable()` | удалить/переименовать `.dll` или подсунуть битый PTX → приложение стартует на CPU |
| 7 | **Версия алгоритма в файле** | после смены палитры старые файлы расшифровываются в «шум» без сообщения | `algorithmVersion` в заголовке; при несовпадении — внятная ошибка, а не мусор |

### P1. Устойчивость и наблюдаемость

| # | Задача | Суть |
|---|---|---|
| 8 | Один GPU-контекст на процесс | `cuDevicePrimaryCtxRetain` + `cuCtxSetCurrent`/`Pop`, `cuDevicePrimaryCtxRelease` при shutdown (сейчас контекст не освобождается) |

### P2. Производительность (то, ради чего всё затевалось)

| # | Задача | Почему важно |
|---|---|---|
| 15 | Валидация фрактала на GPU | сейчас CPU-валидация проходит по 2 млн пикселей с `new float[3]` на пиксель **на каждого кандидата** — по закону Амдала это съедает весь выигрыш генерации |

## 2. Как измерить: три уровня

### Уровень 1. CLI-бенчмарк (добавлен в репозиторий)

`src/main/java/com/cipher/core/benchmark/`:

* `CudaBenchmark` — точка входа, замер и проверка паритета;
* `FractalMetrics` — метрики качества фрактала (доля внутренних точек, занятые бины,
  максимальная доля бина, энтропия тона) **без привязки к типу растра**;
* `ImageDiff` — попиксельное сравнение и SHA-256 «отпечаток» гаммы;
* gradle-таск `benchmarkCuda`.

Запуск:

```powershell
# профиль по умолчанию: 1920x1080, 3 прогрева + 10 замеров, паритет включён
./gradlew benchmarkCuda

# три разрешения, 20 замеров, JSON в конце
./gradlew benchmarkCuda -Pargs="--sizes 640x480,1280x720,1920x1080 --runs 20 --json"

# сетка zoom x maxIter — видно, как выигрыш растёт с глубиной итераций
./gradlew benchmarkCuda -Pargs="--sweep --width 1280 --height 720"

# только CPU-база (CUDA недоступна) — код возврата 2
./gradlew benchmarkCuda -Pargs="--no-parity"
```

Коды возврата: `0` — паритет подтверждён, `1` — **палитры разошлись** (блокер P0 #1),
`2` — CUDA недоступна. То есть таск годится как гейт в CI/пре-коммите: нарушение паритета
валит сборку, а не «незаметно портит данные».

Что печатается:

```
=== Mandelbrot CUDA benchmark ===
cuda available : true
os             : Windows 10 / amd64
cpus           : 16

--- 1920x1080 ---
  CPU 1920x1080 median=412.35 мс [min 401.20, p95 430.10, max 438.02] 1920x1080 internal=12.4% bins=36/36 maxBin=8.9% entropy=4.83 bit OK
  GPU 1920x1080 median=38.10 мс [min 36.11, p95 41.00, max 45.20] 1920x1080 internal=12.4% bins=36/36 maxBin=8.9% entropy=4.83 bit OK
  ускорение генерации фрактала: 10.82x   паритет: 10/10 прогонов
  XOR 1920x1080: CPU 58.20 мс, GPU 4.10 мс, ускорение 14.20x, расхождений 0 px (совместимо)
```

Ключевые числа для отчёта: `ускорение` (генерация и XOR по отдельности), `паритет`
(`0 px` расхождений), `internal/bins/maxBin` — проверка, что GPU-палитра не только
совпадает, но и осталась пригодной как гамма.

### Уровень 2. Тесты (регрессионный гейт)

* `FractalPaletteParityTest` — 4 набора параметров, требует **нулевого** расхождения,
  иначе сообщает, сколько пикселей и насколько разошлось. На исходном коде падает,
  после P0 #1–#2 — зелёный. Без CUDA помечается `skipped` (`Assumptions`).
* `MandelbrotServiceTest` / `ImageEncryptorImplTest` — CPU-путь, работают всегда.
* Критерий для P0 #4: интеграционный тест encrypt→decrypt, оба прогона на GPU-бэкенде
  (сейчас в тестах везде явно CPU-реализации, поэтому дефекты GPU не видны).

### Уровень 3. Интерфейс приложения (пользовательская метрика)

Самое важное для оценки «стало ли лучше пользователю»: до появления GPU-валидации (P2 #15)
время отклика определяется **не** генерацией фрактала.

Что мерить в UI:

1. **Время до первого кадра** — от нажатия «Сгенерировать» до появления изображения в
   `EncryptGenerateController`. Сейчас складывается из `k` генераций и `k` CPU-валидаций.
2. **Число кандидатов до принятия** (`successfulAttempt`) — уже пишется в лог
   «Валидный фрактал найден на попытке N» и в `EncryptedData.attemptCount`.
3. **Время одной валидации** — если оно сравнимо с генерацией на GPU, узкое место найдено.

Практическая оценка без профилировщика: `T_отклик ≈ k·(T_ген + T_вал)`. Если после
переноса генерации на GPU `T_отклик` почти не изменилось, значит доминирует `T_вал`
(пункт P2 #15) — это и есть ожидаемый сейчас результат, потому что валидация осталась
на CPU и аллоцирует `float[3]` на каждый пиксель.

Чтобы проверить это интерфейсно (без правки кода): в окне генерации есть консоль
(`ConsoleManager`), которая выводит попытки; сравните число строк «Попытка N» и
общее время на машине с CUDA и без. Отношение времён при одинаковом числе попыток —
это и есть фактическое ускорение, в отличие от «теоретического» из бенчмарка.

## 3. Порядок работ и ожидаемый эффект

```text
P0 #1–#3   палитра/точность/клэмп   -> 0 px расхождений (бенчмарк: код 0)
P0 #4–#6   типы/контекст/fallback   -> GPU-путь не падает, приложение переживает сбой
P0 #7      версия алгоритма         -> старые файлы отвергаются с сообщением
P1 #8–#14  устойчивость/наблюдаемость
P2 #15     валидация на GPU         -> выигрыш становится заметен в UI, а не только в бенчмарке
P2 #16–#19 аллокации/pinned/batch   -> добираем остаток
```

Ожидаемая картина замеров (по опыту таких ядер, проверяется бенчмарком):

* генерация: выигрыш растёт с `maxIter` и разрешением, упирается в FP64-пропускную
  способность на GeForce (пункт P2 #18 — кандидат на `float`-ядро);
* XOR: почти линейный по памяти, стабильно высокий;
* **сквозной отклик** после P0 но до P2 #15 — невысокий: доминирует CPU-валидация.
  Это главный вывод, который и должен попасть в отчёт о параллелизации.

### Известные ограничения реализации

1. **PTX-файлы не приложены.** Fallback-путь `KernelCompiler` ищет `/cuda/*.ptx`; в репозитории
   их нет, поэтому при отсутствии NVRTC ядро не загрузится и бэкенд уйдёт на CPU (корректно,
   но без ускорения). Собрать на целевой машине:
   `nvcc --fmad=false -ptx mandelbrot.cu -o mandelbrot.ptx` (и так же для `xor.cu`, `validate.cu`),
   положить рядом с `.cu` в `src/main/resources/cuda/`.
2. **Валидация на GPU не отменяет CPU-подтверждение.** По требованию «первый успех
   перехватывает CPU» кандидат, прошедший проверку, дополнительно валидируется на CPU.
   Отбракованные кандидаты на CPU не пересчитываются — именно это и было узким местом.
3. **`cuMemAllocHost` ограничен лимитом ОС** на закреплённую память; при отказе реализован
   pageable-путь, поэтому функциональность не страдает, только скорость копирования.
