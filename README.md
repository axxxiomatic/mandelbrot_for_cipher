# Шифр на множестве Мандельброта

Изображение шифруется XOR'ом с фракталом Мандельброта: параметры фрактала выводятся из общего
секрета ECDH, поэтому гамма у отправителя и получателя совпадает, а у постороннего — нет.
Проект — JavaFX-приложение на Spring Boot.

---

## Требования

| | |
|---|---|
| ОС | **Windows x86_64** — единственная поддерживаемая платформа GPU-контура |
| JDK | 21+ |
| GPU (опционально) | NVIDIA, драйвер **550+** для предсобранного PTX либо любой поддерживаемый NVRTC-компиляцией |
| Сеть | исходящий доступ к `repo1.maven.org` (Gradle скачивает `jcuda-natives`) |
| CUDA Toolkit (опционально) | нужен **только** для NVRTC-компиляции ядер; без него работает предсобранный PTX, а без него — CPU |

Без NVIDIA-карты, без драйвера или при отключённом GPU приложение **работает полностью** —
на CPU-бэкенде, просто медленнее. Это штатный режим, а не ошибка.

## Запуск

1. `Run` → `Edit Configurations` → `+` → `Gradle`
2. **Run**: задача `run`
3. `Apply` → `OK`

Либо из консоли:

```powershell
.\gradlew run
```

## Бэкенды: CPU / CUDA

Выбор автоматический:

```
запрос CUDA  ->  primary context  ->  NVRTC компилирует .cu под вашу карту
                                            |  сбой (нет .dll, нет NVRTC, старый драйвер)
                                            v
                                     предсобранный PTX
                                            |  сбой (PTX новее драйвера)
                                            v
                                          CPU
```

Любая ошибка на этапе инициализации GPU не роняет приложение: `GpuBackends` ловит её,
пишет в лог и возвращает CPU-реализацию. Имя активного бэкенда пишется в лог при старте
(«Бэкенд GPUFractalGenerator активен» / «… переключаюсь на CPU»).

**Про NVRTC и зависимости.** Отдельного артефакта `org.jcuda:jnvrtc` в Maven Central нет:
Java-классы `jcuda.nvrtc.JNvrtc` поставляются внутри `org.jcuda:jcuda`, а нативные
`JNvrtc-*.dll` — внутри `jcuda-natives`. Сам JNI-слой загружает `nvrtc64_*.dll`, которая
устанавливается **только с CUDA Toolkit**, поэтому «драйвер + jcuda-natives» недостаточно
для NVRTC-пути; без Toolkit используется предсобранный PTX, а без него — CPU.

Переключатели:

```powershell
# принудительно CPU (отладка, «полуживой» драйвер, воспроизведение бага)
.\gradlew run -Dcipher.cuda=false
```

## Почему палитра общая

Фрактал здесь — **криптографическая гамма**, а не картинка. Если CPU и GPU посчитают хоть один
пиксель по-разному, файл, зашифрованный на машине с CUDA, не расшифруется на машине без неё:
XOR с другой гаммой даёт шум, а не «слегка иной» результат.

Поэтому:

* вся арифметика палитры — в `FractalPalette`, одна на оба бэкенда;
* только IEEE-операции (`+ − × ÷ sqrt floor`), без `log/exp/pow` — `Math.log` и CUDA `log`
  не совпадают бит-в-бит;
* ядро компилируется с `--fmad=false`, иначе компилятор склеит выражения в FMA и число
  итераций у границы множества разойдётся;
* `FractalPaletteParityTest` требует **0** различающихся пикселей на 4 наборах параметров
  (без CUDA тест помечается `skipped`).

## Версия алгоритма в файле

Заголовок зашифрованного файла:

```
algorithmVersion (4) | salt (16) | attempts (4) | 6 × int геометрии | данные
```

При смене палитры версия увеличивается. Файл, зашифрованный другой версией, **отвергается
с явной ошибкой**: «палитра гаммы изменилась, расшифровка невозможна». Раньше такой файл
«успешно» расшифровывался в мусор.

## Бенчмарк и проверка паритета

```powershell
# профиль по умолчанию: 1920x1080, 3 прогрева + 10 замеров, паритет включён
.\gradlew benchmarkCuda

# несколько разрешений, JSON в конце
.\gradlew benchmarkCuda -Pargs="--sizes 640x480,1280x720,1920x1080 --runs 20 --json"

# сетка zoom x maxIter
.\gradlew benchmarkCuda -Pargs="--sweep --width 1280 --height 720"
```

Коды возврата: `0` — паритет подтверждён, `1` — **палитры разошлись** (несовместимость
шифрования), `2` — CUDA недоступна. Таск годится как гейт в CI.

## Что измеряется и где узкое место

Отклик интерфейса ≈ `k · (T_генерации + T_валидации)`, где `k` — число кандидатов до первого
пригодного. Валидация вынесена на GPU (`validate.cu` считает гистограмму тона и долю внутренних
точек одним запуском ядра), поэтому после переноса генерации на CUDA узким местом остаётся
не перебор пикселей на CPU, а `k` — то есть качество генератора параметров.

Число кандидатов пишется в лог («Валидный фрактал найден на попытке N») и в `attemptCount`
файла. Если оно велико — оптимизировать нужно диапазоны `generateParams`, а не ядро.

## Ограничения, о которых честно

* `float`-ядро (P2 #18 плана) **не делалось**: при `maxIter ≤ 1250` расхождение с `double`
  у границы множества превышает ноль пикселей, а ноль — обязательное требование паритета.
  Измерено: палитра во `float` даёт 246 расхождений на 4 млн пикселей, smooth+hue в `double` — 0.
* GPU-контур не тестировался на реальной карте в этой среде разработки (нет GPU, нет Windows):
  логика проверена парсером и ревью, но `FractalPaletteParityTest` и `benchmarkCuda` должны
  быть прогнаны на целевой машине.
* Кроссплатформенные natives не поддерживаются сознательно: только Windows x86_64.
